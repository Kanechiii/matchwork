## Architecture and Evidence

Azure Container Apps is attached to the secure virtual network. Redis DNS resolves to the private endpoint `10.42.1.4`; discovered Redis shards on ports `8500` and `8501` were TCP-reachable. Certificate hostname checks initially failed because the cluster advertised private IPs. Redis-py's `address_remap` was tested to preserve hostname verification by remapping to the service hostname while keeping shard ports. Never replace this with a blanket `ssl_check_hostname=False` production setting.

On the deployed image, Python redis-py 6.4.0 loaded `RedisCluster` successfully. A one-process `SharedAttemptLedger.reserve(100,1000)` test reported `Reservation: SUCCESS`. The feature was subsequently enabled and Azure showed revision 0000005 healthy. The user reported that the browser UI plays, pauses and displays a recap. That last observation **does not alone prove that the recap was generated by Foundry rather than deterministic fallback**.

Smoke-test the URL after each deploy. For failures inspect `az containerapp logs show --name matchwork-secure-demo --resource-group rg-matchwork-hosting --type console --tail 50` without publishing secrets.

## Limitations

The shared Redis ledger bounds this application's **model call attempts**, not total Microsoft Foundry billing. Azure budget alerts do not stop inference automatically. The backend paid API is bearer-protected; public browser access requires a separate approved identity/session design. The specialist workflow is implemented but its public UI activation and a live model-backed explanation are separate verification gates.
